Porter Earnest Mode 3 / Mode 2 + BCPE sur Claude Code, VS Code Copilot et Cursor

État des lieux des mécanismes d'extension (MCP servers, hooks PreToolUse, rules/skills) et matrice de portage du workflow Spec-First d'Earnest (invariants scellés SHA-256, shadow worktree, base de connaissances d'expérience) vers les trois harnais agentiques majeurs.

1. Rappel du workflow à porter

Mode 3 — Spec-First / Architecture. L'agent (ou l'humain) conçoit la spec et déclare des invariants (contrats C1..Cn) accompagnés de probes polymorphes (inspection AST statique + tests dynamiques CLI). Les invariants sont sérialisés dans .ide/invariants.json, hachés en SHA-256 et scellés dans .ide/invariants.lock en lecture seule (0o444). Aucune mutation sans sign-off humain.

Mode 2 — Implémentation contrainte / Shadow Worktree. Chaque patch candidat est appliqué dans un worktree git isolé (.ide/shadow_worktree), compilé et testé. La fusion atomique vers l'arbre de travail réel n'a lieu que si 100 % des probes passent ; sinon le patch est rejeté avec trace, l'arbre réel reste intact.

BCPE — Base de Connaissances d'Expérience. Serveur MCP stdio (kb serve, SQLite + FTS5) exposant kb_search, kb_get, kb_check, kb_report_incident, kb_propose, kb_record_outcome, kb_confirm, kb_attach_repro. Interrogée en Mode 3 pour éviter de reproduire des erreurs d'architecture connues ; alimentée en Mode 2 par les incidents observés. Le texte d'une entrée est une donnée, jamais une instruction.

2. Claude Code — mécanismes d'extension

2.1 MCP servers

Configuration via claude mcp add ou fichiers JSON : .mcp.json (scope projet, versionnable), ~/.claude.json (scope user), scopes locaux, et serveurs fournis par plugin. Transports : http (alias streamable-http, recommandé pour le distant), sse, ws, stdio. Une entrée avec url mais sans type est une erreur de configuration (interprétée comme stdio). Expansion de variables d'environnement supportée dans .mcp.json. Les outils apparaissent sous la forme mcp__<serveur>__<outil>.

{
  "mcpServers": {
    "bcpe": {
      "type": "stdio",
      "command": "/path/to/Ernest/earnest-bcpe/target/release/kb.exe",
      "args": ["serve", "--db", "/path/to/Ernest/earnest-bcpe\\kb.db"]
    }
  }
}

2.2 Hooks — dont PreToolUse

Les hooks sont des commandes shell, endpoints HTTP, appels d'outils MCP, prompts LLM ou sous-agents exécutés automatiquement à des points du cycle de vie. Ils se déclarent dans les settings (~/.claude/settings.json, .claude/settings.json) ou via un plugin. Événements clés : SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, PostToolUseFailure, SubagentStart/Stop, PreCompact, Stop, SessionEnd, InstructionsLoaded, FileChanged, PreModelSwitch…

PreToolUse reçoit sur stdin un JSON décrivant l'appel (tool_name, tool_input) et peut renvoyer une décision de permission (allow / deny / ask) avec un motif. Un matcher filtre par nom d'outil (regex, ex. Bash|PowerShell, mcp__bcpe__.*) et une condition if affine par sous-commande (Bash(rm *)). Code de sortie 2 = blocage avec message remonté au modèle.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Write|Edit|MultiEdit",
        "hooks": [
          { "type": "command",
            "command": "powershell.exe",
            "args": ["-NoProfile","-ExecutionPolicy","Bypass","-File",
                     "${CLAUDE_PROJECT_DIR}/.claude/hooks/guard-invariants.ps1"] }
        ]
      }
    ]
  }
}

Le script lit le JSON sur stdin, vérifie si la cible est sous .ide/invariants.lock ou .ide/invariants.json et renvoie :

{"hookSpecificOutput":{"hookEventName":"PreToolUse",
 "permissionDecision":"deny",
 "permissionDecisionReason":"Invariants scelles (SHA-256, 0444) : mutation interdite en Mode 2"}}

Variantes utiles : hooks prompt-based (un LLM juge la condition), hooks agent-based (un sous-agent instruit), hooks HTTP, hooks asynchrones en arrière-plan, et hooks déclarés dans les skills/agents (avec limites).

2.3 Skills et rules

Skills : dossier .claude/skills/<nom>/SKILL.md avec frontmatter (name, description, allowed-tools, disable-model-invocation…). Le corps ne charge qu'à l'usage (coût de contexte quasi nul au repos). Invocation par /nom ou automatique. Supporte fichiers annexes, injection de contexte dynamique (!`commande`), exécution en sous-agent, arguments. Les anciennes .claude/commands/ sont fusionnées dans les skills. Claude Code suit le standard ouvert Agent Skills avec des extensions propriétaires.

Rules : CLAUDE.md (toujours chargé) et .claude/rules/*.md (chargés à la demande, événement InstructionsLoaded).

3. VS Code Copilot — mécanismes d'extension

MCP servers

  • Configuration dans .vscode/mcp.json (workspace) ou dans les settings utilisateur ; clé racine servers.
  • Transports : stdio, http, sse.
  • Secrets via inputs + ${input:id} : jamais de token en clair dans le fichier versionné.
  • Découverte via le MCP registry et la commande MCP: Add Server.
  • Outils exposés dans le picker d'outils et référencés par #tool dans le chat.
  • Approbations par outil et sandboxing de l'agent (Approvals and Permissions).

Agent hooks (preview)

  • Fichiers .github/hooks/*.json (workspace) ou dossier utilisateur ; édition via l'Agent Customizations editor.
  • Format : {"version":1,"hooks":{"preToolUse":[{"type":"command","command":"..."}]}}.
  • Événements en camelCase : preToolUse, postToolUse, sessionStart, sessionEnd, userPromptSubmit, stop.
  • Payload JSON sur stdin, réponse JSON sur stdout (allow/deny, contexte additionnel).
  • Harnais multiples : Copilot (partagé avec Copilot CLI et l'app GitHub Copilot), Claude, Codex — chacun avec son propre schéma.
  • Harnais Local déprécié (retrait annoncé février 2027).
  • Hooks agent-scoped déclarés dans les fichiers d'agents personnalisés.
  • Restrictions possibles via les managed settings d'entreprise.

Instructions / Skills / Agents

  • .github/copilot-instructions.md : instructions projet toujours chargées.
  • *.instructions.md avec frontmatter applyTo (globs) : application ciblée par fichiers.
  • AGENTS.md supporté.
  • Agent Skills : dossiers SKILL.md, standard ouvert ; emplacements .github/skills/, .claude/skills/, ~/.copilot/skills/.
  • Prompt files .prompt.md invoqués par /nom.
  • Custom agents .github/agents/*.agent.md (outils, modèle, instructions).
  • Agent Plugins (marketplace) pouvant embarquer skills, hooks et serveurs MCP.

4. Cursor — mécanismes d'extension

MCP servers

  • Configuration dans .cursor/mcp.json (projet) ou ~/.cursor/mcp.json (global) ; clé mcpServers.
  • Transports : stdio, SSE, Streamable HTTP.
  • Capacités : tools, prompts, resources, roots, elicitation, MCP Apps (UI interactive retournée par un outil).
  • OAuth statique (auth.CLIENT_ID / CLIENT_SECRET) ou enregistrement dynamique ; redirects fixes http://localhost:8787/callback et https://www.cursor.com/agents/mcp/oauth/callback.
  • Interpolation ${env:VAR} pour les secrets.
  • Marketplace Cursor + cursor.directory ; distribution team/enterprise.
  • En cloud, les outils MCP apparaissent sous MCP:<tool_name>.

Hooks

  • Fichiers .cursor/hooks.json (projet) ou ~/.cursor/hooks.json (utilisateur) ; rechargement automatique.
  • Processus spawnés, JSON bidirectionnel sur stdio.
  • Hooks agent : sessionStart, sessionEnd, preToolUse, postToolUse, postToolUseFailure, subagentStart, subagentStop, beforeShellExecution, afterShellExecution, beforeMCPExecution, afterMCPExecution, beforeReadFile, afterFileEdit, beforeSubmitPrompt, preCompact, stop, afterAgentResponse, afterAgentThought.
  • Hooks Tab : beforeTabFileRead, afterTabFileEdit. Hook applicatif : workspaceOpen.
  • Types : command (défaut) et prompt (évalué par un LLM).
  • Windows : exécution via PowerShell, JSON lu depuis $input.
  • Compatibilité hooks Claude Code (Third Party Hooks) : réutilisation directe possible.
  • Cloud agents : hooks projet/team/enterprise uniquement (pas de hooks utilisateur).

Rules / Skills / Subagents

  • Project Rules : .cursor/rules/*.mdc avec frontmatter description, globs, alwaysApply.
  • 4 modes : Always Apply / Apply Intelligently / Apply to Specific Files / Apply Manually (@rule).
  • User Rules (globales), Team Rules (dashboard, Team/Enterprise), AGENTS.md.
  • Agent Skills : .cursor/skills/, .agents/skills/, ~/.cursor/skills/, ~/.agents/skills/ — et compatibilité .claude/skills/, .codex/skills/.
  • Skills imbriqués par sous-dossier, scopés automatiquement au répertoire.
  • Subagents (/create-subagent), Custom Modes, Plugins.
  • Skills intégrés : /create-rule, /create-hook, /create-skill, /migrate-to-skills.

6. Recettes de portage du workflow Earnest

6.1 Mode 3 — Spec-First (geler les invariants)

Objectif Earnest : produire .ide/invariants.json, le sceller en SHA-256 dans .ide/invariants.lock (lecture seule 0444), puis interdire toute mutation sans sign-off humain.

Claude Code

  • Skill .claude/skills/mode3-spec/SKILL.md : procédure de conception + format des probes.
  • Hook PreToolUse sur Write|Edit avec if ciblant invariants.lock → permissionDecision: "deny".
  • Hook Stop : vérifie que le lock existe et que son SHA-256 correspond.
  • Hook InstructionsLoaded : injecte le rappel « invariants scellés ».

VS Code Copilot

  • Skill .github/skills/mode3-spec/SKILL.md (même contenu, portable).
  • Hook preToolUse dans .github/hooks/seal.json : refuse l'écriture sur invariants.lock.
  • Instructions *.instructions.md avec applyTo: ".ide/**" pour le rappel de contrat.
  • Custom agent architect.agent.md restreint aux outils de lecture + add_invariant.

Cursor

  • Skill .cursor/skills/mode3-spec/SKILL.md (ou .agents/skills/).
  • Hook preToolUse + beforeReadFile dans .cursor/hooks.json.
  • Rule .cursor/rules/invariants.mdc avec globs: .ide/**, alwaysApply: false.
  • Hook stop : contrôle d'intégrité du lock avant clôture du tour.

6.2 Mode 2 — Shadow Worktree (implémentation contrainte)

Objectif Earnest : tout patch est appliqué dans .ide/shadow_worktree/, validé par probes statiques (AST) et dynamiques (CLI), puis fusionné atomiquement seulement si 100 % PASS. Sinon : rejet, trace, arbre de travail intact.

Claude Code

  • Hook PreToolUse sur Write|Edit : réécrit updatedInput pour rediriger le chemin vers .ide/shadow_worktree/.
  • Hook PostToolUse : lance cargo test / pytest + inspection AST ; en cas d'échec, additionalContext avec la trace.
  • Hook PostToolBatch : vérifie l'ensemble des probes avant le tour suivant.
  • Hook Stop : bloque la fin de tour si des probes n'ont pas tourné.
  • Subagent verifier en contexte isolé pour l'arbitrage.

VS Code Copilot

  • Hook preToolUse : validation/redirection du chemin d'écriture.
  • Hook postToolUse : exécution des probes et retour du verdict.
  • Hook stop : refus de clôture si verdict incomplet.
  • Custom agent implementer.agent.md avec outils limités au worktree.
  • Limite : pas de PostToolBatch ni de PreCompact → arbitrage par lot à simuler dans le hook stop.

Cursor

  • Hook preToolUse : redirection vers le worktree (Cursor ignore updated_input pour les outils MCP distants, mais l'accepte pour les outils locaux).
  • Hook afterFileEdit : formate puis déclenche les probes.
  • Hook beforeShellExecution : n'autorise que les runners déclarés (cargo test, pytest).
  • Hook stop : vérifie le verdict global.
  • Hook subagentStop : arbitrage du sous-agent de vérification.

7. Recommandations et limites

Portabilité maximale

  • Placer les skills dans .claude/skills/ : les trois outils les lisent (Cursor et Copilot supportent explicitement ce répertoire).
  • Utiliser le standard ouvert Agent Skills pour le contenu, et réserver les extensions propriétaires au strict nécessaire.
  • Garder les scripts de hooks en PowerShell (Windows) ou en Python portable, avec lecture JSON sur stdin.
  • Centraliser la logique métier (scellement, probes, arbitrage) dans le binaire kb / earnest-core et laisser les hooks n'être que de fins adaptateurs.

Limites à anticiper

  • VS Code Copilot : hooks en preview, surface d'événements plus étroite (pas de PostToolBatch, PreCompact, SubagentStop).
  • Cursor : updated_input ignoré pour les outils MCP distants ; hooks utilisateur absents en cloud agents.
  • Claude Code : surface la plus riche mais la plus spécifique ; les hooks ne sont pas portables tels quels vers les deux autres sans adaptation du schéma.
  • Nommage : PreToolUse (PascalCase) vs preToolUse (camelCase) — source d'erreurs fréquente lors du portage.
  • Sécurité : un hook s'exécute sans validation du modèle ; revoir chaque script avant installation, surtout depuis une marketplace.

8. Conclusion

Les trois outils convergent vers un même modèle en trois couches : MCP pour les capacités (BCPE), hooks pour le contrôle (scel des invariants, shadow worktree, arbitrage), et skills/rules pour la connaissance (procédure Mode 3, conventions Mode 2). Le workflow Earnest est donc portable dans son architecture, mais pas dans ses fichiers : chaque cible exige un adaptateur de schéma de hooks, tandis que les skills et le serveur MCP BCPE restent, eux, directement réutilisables.

La stratégie la plus robuste consiste à faire de earnest-bcpe et earnest-core les véritables détenteurs de la logique de gouvernance, exposés via MCP, et à réduire les hooks de chaque IDE à de simples points d'entrée déclenchant ces binaires. On obtient alors un comportement identique sur Claude Code, VS Code Copilot et Cursor, indépendamment des évolutions de leurs API d'extension respectives.
